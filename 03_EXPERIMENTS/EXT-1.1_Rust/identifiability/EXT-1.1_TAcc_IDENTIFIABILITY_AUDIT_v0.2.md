# EXT-1.1 Rust — `T_acc` Identifiability Adversarial Audit v0.2

**Audit target:** `EXT-1.1_TAcc_IDENTIFIABILITY_PROTOCOL_v0.2.md`
**Audit type:** second adversarial audit
**Status:** COMPLETE — revision required; protocol not frozen
**Decision:** **CONDITIONAL FAIL / NOT YET IDENTIFIABLE**

## 1. Audit objective

Attempt to falsify the revised operationalization of `T_acc` before any scientific Rust dataset is processed.

The audit specifically targets the corrections introduced after v0.1:

1. separation of `S_t` and `C_t`;
2. technical/registry-resolvable accessibility;
3. finite counterfactual candidate universe `U_t`;
4. separation of `T_acc,t` from `T_real,t`;
5. temporal non-leakage;
6. deterministic Cargo resolution;
7. the accessible-but-unrealised counterfactual fixture.

## 2. Executive verdict

The v0.2 protocol is materially stronger than v0.1 and resolves the broad conceptual failures identified in the first audit. However, it is **not yet sufficient for freeze**.

The remaining problems are operational rather than a rejection of the Rust domain:

- the exact boundary of `S_t` is still underspecified;
- the candidate transformation operators are not yet sufficiently canonical;
- `U_t` is declared finite but its exact generation algorithm and bounds are not frozen;
- the resolver/environment specification is required but not yet defined as an auditable input;
- the counterfactual fixture is required but has not yet been instantiated;
- reproducibility therefore remains conditional rather than demonstrated.

The central construct remains potentially identifiable if these issues are resolved before scientific processing.

## 3. A1 — Unit audit

**Verdict: PARTIAL PASS**

The explicit distinction between package state `S_t` and external context `C_t` is correct and is a substantial improvement over v0.1.

However, `S_t` is defined as the exact package version plus manifest-level dependency declarations and "other frozen package attributes required by the transformation model." This remains open-ended. A reproducible experiment cannot leave the membership of `S_t` to later analyst judgement.

### Required correction

Define `S_t` as an explicit machine-readable record containing every package-local field that can affect construction or evaluation of the candidate dependency transformation. At minimum, the freeze specification must enumerate:

- package identity and version;
- complete manifest dependency declarations relevant to the experiment;
- dependency kinds included/excluded;
- target/platform conditions included/excluded;
- optional dependencies and feature declarations if they affect resolution;
- package edition and resolver-relevant manifest metadata.

Any field not included must be explicitly declared irrelevant to `F`.

## 4. A2 — Transformation audit

**Verdict: PARTIAL PASS**

The protocol correctly removes publication as a primitive and restricts `tau` to machine-representable dependency-configuration changes.

Two weaknesses remain.

First, operators 3 and 4 partially overlap: "replace a declared dependency requirement" and "change a declared dependency requirement to another pre-specified valid requirement form" do not define a unique canonical operation.

Second, "add a dependency declaration" does not specify the complete parameterisation of the added declaration. A declaration may vary by package identity, version requirement, source, feature set, optionality, target condition, and dependency kind.

### Required correction

Define `tau` as a canonical tuple generated by a finite operator grammar. The protocol must specify exactly which dependency fields may change and which are held fixed.

For the initial confirmatory experiment, a deliberately austere primitive is preferable: one registry dependency edge with one concrete candidate package/version requirement, under a fixed dependency kind, feature policy, and target policy.

Broader dependency transformations can be treated as extensions only after the minimal construct passes identifiability.

## 5. A3 — Accessibility audit

**Verdict: CONDITIONAL PASS / NOT YET DECIDABLE**

The move from generic "feasibility" to registry-resolvable accessibility is conceptually sound. It avoids claims about developer intent, implementation effort, adoption, or success.

The remaining issue is that "deterministic Cargo dependency-resolution solution under the frozen resolver semantics" is named but not actually frozen in v0.2.

Cargo resolution can depend on resolver generation/version and relevant configuration. The experiment therefore cannot treat "Cargo resolution" as a black box while claiming deterministic accessibility.

### Required correction

Create a separate resolver specification artifact before protocol freeze containing:

- exact Cargo version/toolchain used for confirmatory resolution;
- resolver generation selected for the experiment;
- relevant manifest/resolver configuration;
- registry source definition;
- handling of yanked versions;
- feature-resolution policy;
- target/platform policy;
- any source replacement or configuration that can alter resolution;
- deterministic invocation procedure.

The accessibility predicate must reference this frozen specification by version/hash.

## 6. A4 — Candidate-universe audit

**Verdict: FAIL — recoverable**

The protocol correctly prohibits future transitions from defining `U_t`, and it correctly requires candidate package/version identifiers to come from the historical registry snapshot.

However, finiteness is asserted rather than operationally demonstrated. A historical registry contains a finite set of package/version records, but the transformation operator may still generate multiple requirement forms, feature combinations, target conditions, and other parameter combinations unless these are explicitly bounded.

This is the most important remaining identifiability gap.

### Required correction

Specify an explicit finite construction such as:

`U_t = Operators × EligiblePackageVersions(C_t) × FixedParameterDomain`

where every factor is finite and its membership rule is frozen before analysis.

For the minimal confirmatory experiment, the parameter domain should be reduced as far as scientifically defensible: registry source fixed, dependency kind fixed, target policy fixed, feature policy fixed, and one canonical requirement representation per candidate package/version.

No analyst-selected filtering may be introduced after observing realised transitions.

## 7. A5 — State/context sufficiency audit

**Verdict: PARTIAL FAIL — recoverable**

The equation `T_acc,t = F(S_t, C_t)` is now structurally correct.

Nevertheless, `C_t` is still defined broadly as the historical registry/index state "and other explicitly frozen environmental information". This leaves the model vulnerable to hidden environment leakage.

In particular, the resolver/toolchain semantics required by A3 must have an explicit location in the frozen input model. Otherwise two researchers can use the same `(S_t,C_t)` but different resolution semantics and obtain different `T_acc,t`.

### Required correction

Either:

`T_acc,t = F(S_t, C_t, R)`

where `R` is a separately hashed and immutable resolver specification, or incorporate `R` explicitly into `C_t` and define it completely.

The preferred scientific representation is to retain the distinction:

- `S_t` = package state;
- `C_t` = contemporaneous historical registry/context;
- `R` = frozen measurement/resolution rules.

This makes the source of determinism auditable.

## 8. A6 — Reproducibility audit

**Verdict: FAIL FOR FREEZE — CONDITIONAL PASS IN DESIGN**

The protocol now lists the correct classes of reproducibility evidence, including hashes, machine-readable output, historical context, and resolver semantics.

But no actual resolver specification or machine-readable `T_acc` fixture has yet been frozen, and no independent reconstruction has yet been demonstrated.

C3 provides useful reproducibility infrastructure, including frozen Cargo artifacts and checksum verification, but C3 does not establish scientific `T_acc` reproducibility.

### Required correction

Before freeze, produce a minimal executable fixture with:

- exact `S_t`;
- exact historical `C_t`;
- exact resolver specification `R`;
- finite `U_t`;
- computed `T_acc,t`;
- computed `T_real,t` where applicable;
- expected outputs committed in machine-readable form;
- SHA-256 hashes;
- a second independent verification path or hand-verifiable calculation.

## 9. A7 — Discriminability audit

**Verdict: PASS IN PRINCIPLE / FIXTURE REQUIRED**

The revised protocol now explicitly permits accessible transformations that were never realised. This is sufficient in principle to prevent `T_acc` from collapsing definitionally into the observed trajectory.

However, the required fixture has not yet been instantiated. Therefore the distinction is specified but not yet empirically demonstrated.

### Required fixture

At least one candidate must satisfy:

`tau ∈ T_acc,t` and `tau ∉ T_real,t`.

At least one candidate must satisfy:

`tau ∉ T_acc,t` and `tau ∉ T_real,t`.

At least one observed transformation must be evaluated independently for prior accessibility.

## 10. Temporal leakage adversarial test

**Verdict: PASS AT PROTOCOL LEVEL / IMPLEMENTATION CONTROL REQUIRED**

The v0.2 prohibition on current/future registry information, future releases, future lockfiles, adoption outcomes, survival outcomes, and observed next states is explicit and adequate at the conceptual level.

The remaining risk is implementation: the historical `C_t` must actually be reconstructed from a dated snapshot rather than derived from the current registry and filtered retrospectively.

### Required control

The implementation must preserve the exact historical snapshot artifact and its hash. The analysis code must accept that snapshot as an explicit input and must not query a live registry during historical `T_acc,t` construction.

## 11. Adversarial findings

### F1 — Open-ended state definition

If "other frozen package attributes" remains undefined, `S_t` can expand after seeing results. This violates reproducibility.

**Disposition:** revise A1.

### F2 — Operator parameter explosion

A dependency transformation is not finite merely because package/version identifiers are finite. Features, target predicates, dependency kinds, and requirement representations can multiply the candidate space.

**Disposition:** revise A2/A4; begin with an austere canonical operator.

### F3 — Resolver semantics leakage

A historical registry snapshot alone does not fully specify the computation if resolver/toolchain/configuration choices remain implicit.

**Disposition:** create and hash resolver specification `R`.

### F4 — Historical availability versus syntactic reference

A package/version identifier being present in an index is not by itself sufficient evidence that the complete candidate dependency configuration is resolvable. The actual resolver test must remain the decisive accessibility predicate.

**Disposition:** retain the two-stage rule: candidate generation from historical metadata, accessibility from deterministic historical resolution.

### F5 — Realised-event contamination

`T_real,t` must remain a downstream classification. Future observed transitions may identify whether a candidate was realised, but must never influence candidate generation or accessibility.

**Disposition:** PASS, with implementation test required.

### F6 — C3 portability overclaim

C3 demonstrates prepared historical offline resolution and artifact integrity, but not a clean-machine self-contained scientific environment.

**Disposition:** retain C3 qualification; do not use it as evidence that v0.2 is independently reproducible.

### F7 — Scientific scope of accessibility

Registry-resolvable accessibility is a deliberately narrower construct than the full TGCV notion of what a system can transform. This is acceptable only if the experiment explicitly identifies it as a domain-specific operationalization and does not silently generalise it to authorial or implementation feasibility.

**Disposition:** PASS, provided the scope limitation remains explicit in the frozen protocol and subsequent claims.

## 12. Required v0.3 revisions

Before freeze, the protocol should be revised to v0.3 with the following mandatory changes:

1. make `S_t` an explicit enumerated machine-readable state schema;
2. canonicalise the primitive `tau` and its parameter domain;
3. define `U_t` with an explicit finite construction algorithm;
4. introduce frozen resolver specification `R` explicitly;
5. define all resolver/environment parameters relevant to accessibility;
6. instantiate the three-case hand-verifiable counterfactual fixture;
7. define the exact historical snapshot input and hashing procedure;
8. prohibit live-registry access during historical computation;
9. specify the machine-readable output schema for `T_acc,t` and `T_real,t`;
10. preserve the explicit limitation that the construct measures technical registry-resolvable accessibility, not intent, implementation success, adoption, or survival.

## 13. Decision

**FINAL AUDIT VERDICT: CONDITIONAL FAIL / REVISION REQUIRED.**

The v0.2 operationalization is substantially improved and appears scientifically recoverable, but it does not yet satisfy the evidentiary threshold for freeze.

**Scientific dataset processing remains BLOCKED.**

The correct next step is **v0.3 protocol revision**, followed by a focused adversarial audit of the finite candidate construction and frozen resolver specification, and only then the final freeze decision.
