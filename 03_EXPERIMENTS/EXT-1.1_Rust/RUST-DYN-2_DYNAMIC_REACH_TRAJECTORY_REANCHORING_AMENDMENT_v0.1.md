# TGCV — RUST-DYN-2 Dynamic Reach / Trajectory Re-Anchoring Amendment v0.1

**Status:** DESIGN AMENDMENT — EXECUTION NOT AUTHORIZED
**Date:** 2026-09-08

## 1. Purpose

Re-anchor RUST-DYN-2 to the already frozen Rust Potential Reach semantics established historically, and add only the genuinely new dynamic comparison required by DR-037: `ΔReach¹_pot` and the trajectory dimension.

This amendment does not create a new Reach architecture and does not reopen the historical Reach non-redundancy result accepted by DR-018.

## 2. Reused frozen semantics

The Rust successor semantics are:

`Succ(C,τ) = C \ {(p_d, *)} ∪ {(p_d,v_d)}`

where a dependency declaration's target-package assignment is replaced by a target-version assignment associated with an admissible transformation.

This is a **potential configuration successor**, not execution, not an observed Cargo result, and not a resolver-selected runtime state.

Depth-1 Potential Reach is the set of canonical successor configurations generated by admissible transformations from the focal configuration.

Historical work already established bounded structural Reach non-redundancy and is retained as prior evidence. It is not silently recomputed or replaced.

## 3. Current population

Temporal comparisons use exactly the DR-035 population:

- same package;
- adjacent consecutive origins;
- ordered by `created_at`;
- exact timestamp ties excluded;
- earlier → later.

The historical population has been reconciled exactly with DR-035 on the frozen dataset: 516,061 identical pairs, zero historical-only pairs, zero DR-035-only pairs, and zero timestamp-tie origins.

Therefore historical temporal population compatibility is established.

## 4. Current transformation identity

Current RUST-DYN-2 must use the frozen four-field transformation identity:

`τ = (origin_version_id, target_package_id, target_version_id, target_version_str)`.

Historical three-field representations are retained only as historical artifacts and are not silently substituted for the current identity.

## 5. Dynamic objects

For each DR-035 pair `(o_i,o_j)`:

`T_i = T_acc(o_i)`

`T_j = T_acc(o_j)`

`R_i = Reach¹_pot(o_i)`

`R_j = Reach¹_pot(o_j)`

`ΔT = 1[T_i ≠ T_j]`

`ΔR = 1[R_i ≠ R_j]`

Reach equality is exact canonical configuration-set equality, never cardinality-only.

## 6. Successor configuration identity

A successor identity must be a complete canonical configuration representation sufficient to distinguish the dependency declaration state before and after the potential transformation.

The successor identity is therefore **not** the transformation tuple itself.

For the frozen depth-1 representation, the minimum required identity is the canonicalized focal configuration with the relevant dependency target assignment replaced by the selected target-version assignment implied by the admissible transformation.

No observed execution state, lockfile result, resolver-selected runtime result, future release activity, adoption, downloads, success, outcome, value, or predictive target may enter the successor identity.

## 7. Independence condition

The earlier DR-040 requirement for a separate independent structural successor graph is not retained. DR-041 established that it was a new and unnecessarily stronger requirement relative to the historically frozen Potential Reach semantics.

The required independence for this amendment is instead:

- `T_acc` is constructed from the admissibility predicate;
- `Reach¹_pot` is constructed from the frozen configuration successor operator;
- `Reach¹_pot` is not represented merely as the set of transformation identities;
- `Reach¹_pot` does not use observed execution or outcomes;
- Reach construction does not feed back into `P_τ`.

## 8. Dynamic non-redundancy question

The new test is not whether Reach exists. That is already established.

The new question is whether temporal change in accessible transformations and temporal change in potential successor configurations remain analytically distinguishable.

Required non-degenerate cases:

- **ND-1:** `ΔT = 1`, `ΔR = 0`;
- **ND-2:** `ΔT = 1`, `ΔR = 1`;
- **ND-3:** Reach changes without a one-to-one identity with transformation-set change;
- **ND-4:** equal Reach cardinality but different successor membership;
- **ND-5:** same Reach but different trajectory ordering, if trajectory is representable under the frozen structural object.

Absence of an ND case in H=1 is not by itself proof of redundancy; it is reported as a limitation.

## 9. Trajectory

Trajectory is a new analytical dimension and is not imported from the historical Reach result.

At depth 1, trajectory is an ordered sequence of potential successor configurations. It must preserve path/order information and exclude the initial origin from the successor sequence.

A trajectory is **not** an ordering of `T_acc`.

If the frozen depth-1 structural representation cannot support a non-arbitrary trajectory distinction, no H>1 trajectory claim shall be made. Any extension to H>1 requires a separate design gate.

## 10. Required outputs

The future RUST-DYN-2 executor shall produce:

- exact DR-035 population count;
- `ΔT` / `ΔR` / trajectory contingency cells;
- ND-1..ND-5 witness counts where identifiable;
- exact T_acc hashes;
- exact Reach¹_pot hashes;
- trajectory hashes where applicable;
- canonical successor identities for witnesses;
- dataset, executor and resolver hashes;
- firewall status;
- deterministic output hash;
- primary and replay results.

## 11. Firewall

The implementation must not read or use:

- downloads;
- adoption/popularity/success;
- later release activity;
- future outcomes;
- value labels;
- predictive targets or metrics;
- post-origin metadata;
- execution results;
- lockfile/runtime outcomes;
- retrospective pair selection;
- sampling.

## 12. Scientific boundary

A PASS can support only bounded structural/informational distinction between `ΔT_acc`, `ΔReach¹_pot`, and trajectory under the frozen Rust operationalization.

It cannot establish causality, predictive superiority, universal validity, positive value, or originality.
