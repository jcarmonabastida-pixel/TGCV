# RUST-DYN-STATE-1 — Reach-State Sufficiency Gate v0.1

## Status

**PASS CONDICIONAL — BOUNDED SUCCESSOR-STATE REPRESENTATION ACCEPTED SUBJECT TO NORMALIZATION**

## Purpose

Determine whether the Rust `version_id` representation may be used as a bounded successor-state identifier for the RUST-DYN downstream structural analysis, without claiming that it represents the complete state of the Rust ecosystem or package state.

This gate precedes real-data execution. It does not reopen TR-131 and does not authorize execution of the real dataset.

## 1. Scope

The operational object is the package-version node in the frozen structural transformation graph. A transformation

`τ = (origin_version_id, target_package_id, target_version_id, target_version_str)`

identifies an accessible transition from an origin package-version to a target package-version.

For RUST-DYN, `target_version_id` may therefore serve as a **bounded successor-state identifier** within this graph representation.

This is not equivalent to claiming:

- that `version_id` exhaustively represents the complete state `S`;
- that all package metadata, ecosystem context, dependency environment, or external conditions are encoded by `version_id`;
- that graph successor identity is a sufficient representation for every possible Rust-state analysis.

## 2. Prior bridge evidence

The repository contains the R6 version-ID bridge audit supporting the package-version to `crates.io version_id` mapping used by the existing Rust structural pipeline. That evidence is sufficient for the bounded graph-node interpretation required here, but not for a stronger whole-system state claim.

## 3. Reach normalization decision

The initial origin node is **excluded** from the comparative Reach set.

For horizon `H`:

`Reach_H(o) = { successor nodes reachable from o in 1..H transformation steps }`

The origin itself is not included merely because it is the starting point.

Reason: comparing `Reach_H(o_a)` and `Reach_H(o_b)` must not produce a trivial difference solely because `o_a != o_b`.

## 4. Trajectory normalization decision

Trajectory comparison uses ordered finite-horizon sequences of successor states generated by accessible transformations.

The initial origin identifier is excluded from the comparative trajectory identity. A trajectory is therefore represented as a sequence of successor node identifiers reached after one or more transformations.

This prevents the origin identifier itself from creating a spurious trajectory difference while retaining path order and successor-state structure.

## 5. T_acc remains distinct

The normalization above applies only to Reach and Trajectory comparison.

`T_acc` retains the full canonical transformation identity, including its origin, because the object being compared at the accessibility layer is the set of transformations accessible **from a particular origin**.

Therefore:

- `T_acc` identity includes origin;
- Reach identity excludes the initial origin from the downstream successor set;
- Trajectory identity excludes the initial origin but preserves ordered successors;
- no scalar cardinality substitution is permitted.

## 6. Non-degeneracy requirements

The corrected implementation must preserve the following distinctions:

- ΔT_acc may differ while one-step Reach is equal;
- equal Reach may coexist with different trajectory structure at a larger horizon;
- different origins must not force unequal Reach merely by origin identity;
- different origins must not force unequal Trajectory merely by origin identity;
- exact set comparison remains the basis for ΔT_acc.

## 7. Information firewall

The downstream representation must remain closed against:

- later release activity;
- downloads, adoption, popularity, or success measures;
- future outcome windows;
- predictive targets or predictive metrics;
- post-origin metadata introduced solely to classify accessibility;
- sampling introduced to manufacture downstream differences.

## 9. Decision

**RUST-DYN-STATE-1 = PASS CONDICIONAL.**

The bounded successor-state representation is accepted for RUST-DYN, provided the executable implementation is corrected so that Reach and Trajectory are normalized as specified above.

No real-data execution is authorized by this gate.
