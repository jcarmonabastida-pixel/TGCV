# TI-001 V012 NEXT4 — Future-Structure Generator, Null and Surface-Control Specification 001

**Status:** DESIGN REVIEW — NOT EXECUTION AUTHORIZED  
**Date:** 2026-09-30  
**Parent:** TI001_V012_NEXT4_FUTURE_STRUCTURE_SCHEMA_AND_PERMUTATION_PLAN_001

## 1. Purpose

Define the deterministic generation of future structures and the exact construction principles for the NULL and SURFACE_CONTROL conditions before any NEXT4 fixture is generated.

The design goal is to ensure that the experimental manipulation changes semantic profile→future correspondence without introducing action, value, reward, presentation or complexity leakage.

## 2. Generator contract

The generator is a pure deterministic function: G(seed, structure_id) → canonical_future_structure.

The output depends only on the frozen generator seed and structure identifier.

It must not receive profile_id, action_identity, chosen action, model output, domain, operationalisation, presentation, reward/value/performance fields.

The generator must be executable independently of the decision executor.

## 3. Fixed horizon

The generator uses a single frozen horizon H for all structures.

H must be selected before generation and recorded in the final generator specification.

No structure may use horizon as an experimental condition.

## 4. Structural inventory generation

The generator creates a finite inventory containing matched topology classes:

1. linear;
2. branching;
3. convergence;
4. mixed branching/convergence;
5. multi-step composition.

Each generated graph is accepted only if it satisfies the schema and pre-declared structural matching constraints.

The generator must reject any graph that violates node/edge/horizon bounds.

No graph is accepted because it is associated with a particular action or profile.

## 5. Canonical graph identity

Each accepted graph is canonically serialized and hashed.

The hash is derived exclusively from node topology, edge topology, transformation labels and fixed horizon.

The hash must not depend on profile, action, domain, presentation or condition.

## 6. Structural matching

The inventory must be balanced before fixture construction.

Required matching fields:

- horizon;
- node count;
- edge count;
- label vocabulary.

If exact matching across topology classes is mathematically impossible, the imbalance must be frozen explicitly and treated as a design factor. It may not be corrected after observing scientific results.

No scalar complexity score is used as the dependent or explanatory scientific signal.

## 7. Stable condition

For a matched counterfactual unit, STATIC_CONTROL uses P_i → F_i where the profile/future mapping is fixed by the base mapping.

The future structures themselves are not regenerated between stable and reassigned conditions.

## 8. Future-reassigned condition

FUTURE_REASSIGNED uses the same profile inventory, action inventory and future-structure inventory as its paired stable unit.

Only the mapping changes: P_i → F_pi(i), where pi is a non-identity permutation from the frozen permutation family.

The graph objects are byte-identical to those in the paired stable condition.

## 9. Surface control

SURFACE_CONTROL preserves profile→future mapping, future-structure graph identity, action inventory, domain and operationalisation.

It changes only a pre-specified presentation permutation.

The surface permutation is generated independently from the future-structure permutation and must be balanced against it.

The surface control therefore tests whether an apparent mapping effect can be reproduced by presentation manipulation alone.

## 10. Null construction

UNINFORMATIVE_NULL must remove recoverable profile→future correspondence while preserving the basic representational burden.

The null uses the same future-structure inventory and same graph serialization schema, but the profile association is generated by an independent null mapping.

The null mapping is not used as an informative semantic relation.

For every null unit, the profile→future assignment is sampled from the same balanced permutation space used for informative assignments, but the experimental semantics explicitly declare it uninformative and no stable mapping is presented as the intended correspondence.

The final null presentation must not allow the model to infer a privileged profile→future mapping from position, ordering or labels.

## 11. Null validity criterion

The null passes only if all of the following hold:

- graph inventory is identical to informative conditions;
- presentation burden is matched;
- profile and future namespaces are identical;
- no deterministic profile→future correspondence is privileged;
- null mapping is balanced;
- domain and operationalisation are balanced;
- future-structure identity is not recoverable from presentation.

A random replacement of graphs with unrelated noise is not an acceptable null unless separately justified and frozen.

## 12. Presentation generation

Presentation permutations are generated by a separate deterministic function: P(seed_p, unit_id) → presentation_permutation.

The presentation generator cannot receive future_structure_id, action identity, chosen action or profile→future mapping.

Presentation permutations must be independently balanced.

## 13. Counterfactual construction

For each stable/reassigned pair:

- same profiles;
- same actions;
- same future graphs;
- same domain;
- same operationalisation;
- same replicate family;
- same presentation distribution;
- different profile→future mapping.

For each surface-control pair:

- same semantic mapping;
- same future graphs;
- different presentation permutation.

For each null unit:

- same inventories and surface burden;
- no privileged semantic mapping.

## 14. Leakage audit interface

The generator package must expose machine-readable audit fields sufficient to test:

future_structure_id → action_identity  
future_structure_id → profile_id  
future_structure_id → presentation  
future_structure_id → domain  
future_structure_id → operationalisation

All such associations must satisfy the frozen balance criteria.

The package must also expose the exact mapping table used for each counterfactual unit.

## 15. Determinism and reproducibility

Every generated structure and mapping must be reproducible from frozen seeds.

The final fixture must record:

- generator version;
- generator source hash;
- generator seed;
- structure inventory hash;
- permutation-family hash;
- presentation generator hash;
- null construction hash.

No manual edits are permitted after generation.

## 16. Forbidden generator inputs

The following are hard-blocked:

- action;
- selected action;
- action score;
- model probability;
- reward;
- utility;
- value;
- performance;
- success/failure;
- post-decision state;
- model response;
- presentation metadata.

If any forbidden input is present in the generator interface, semantic gate fails.

## 17. Required tests

Before fixture construction:

1. deterministic replay test;
2. canonical serialization test;
3. graph schema test;
4. topology inventory test;
5. stable/reassigned identity test;
6. surface-control invariance test;
7. null-balance test;
8. action leakage test;
9. profile leakage test;
10. presentation leakage test;
11. domain leakage test;
12. operationalisation leakage test;
13. forbidden-input interface test;
14. counterfactual mapping-difference test.

All tests must pass before fixture freeze.

## 18. Scientific boundary

This specification defines how future structures and controls are constructed. It does not establish that the future structures correspond to T_acc, Reach or Trajectory.

It does not define the statistical model and does not authorize scientific execution.
