## 1. Purpose

This document defines the operational fixture architecture required to implement P1-P3 of the TR-131 second protocol audit.

It is a fixture design, not a scientific result.

The fixture must be capable of demonstrating:

- non-target invariance;
- controlled X contrast;
- transition-level trace generation;
- deterministic derivation of trajectory H.

No fixture preflight output may be treated as TR-131 scientific evidence.

---

## 2. Design principle

The fixture implements the minimal controlled construction:

(S₀,C,T_acc)_A=(S₀,C,T_acc)_B

while:

X_A≠X_B

and permits observation of:

T_real,A, T_real,B, H_A, H_B

The fixture must not encode the expected scientific result.

In particular, it must not force either H_A≠H_B or H_A=H_B.

---

## 3. P1 — Invariance audit implementation

The fixture shall construct one canonical baseline representation and derive both cases from it.

### 3.1 State

S₀ shall be represented as a canonical machine-readable object.

Required outputs:

- canonical serialized S₀;
- SHA-256 hash;
- equality result A/B.

Acceptance:

S₀,A=S₀,B

### 3.2 Context

C shall use the same canonical representation for both cases.

Required outputs:

- canonical serialized C;
- SHA-256 hash;
- equality result A/B.

Acceptance:

C_A=C_B

### 3.3 T_acc

T_acc shall be generated by one deterministic constructor from the frozen baseline.

Each transformation shall have a canonical representation.

Required outputs:

- canonical ordered transformation list;
- cardinality;
- SHA-256 hash;
- A/B equality result.

Acceptance:

T_acc,A=T_acc,B

### 3.4 Rules

The following shall be represented by explicit frozen artifacts or hashes:

- transformation definitions;
- admissibility rules;
- transition function;
- observation window;
- measurement procedure;
- analysis code.

Any mismatch shall produce an invariance failure.

---

## 4. P2 — X declaration implementation

The fixture shall create a declaration record before any realization step.

Minimum schema:

{X_definition, X_A, X_B, admissible_values, instantiation, randomization, timestamp, protocol_id}

The declaration record must be generated independently of trajectory, outcome and value.

Forbidden dependencies:

X=f(H)

X=f(O)

X=f(V)

X=f(T_real)

The fixture shall verify that X is present in the trace before the first realized transformation.

---

## 5. P3 — Transition trace implementation

Each execution shall emit one deterministic transition record per transition.

Minimum logical schema:

| Field | Requirement |
|---|---|
| case_id | A or B |
| step | deterministic integer |
| S_t | canonical state/hash |
| C_t | canonical context/hash |
| T_acc_t | canonical space/hash |
| X_t | declared realization condition |
| T_real_t | realized transformation |
| S_t1 | resulting state/hash |

The trace must permit reconstruction of the complete realized transformation sequence without relying on the terminal state.

---

## 6. Trajectory derivation

H shall be derived exclusively from the frozen trace.

For the first fixture version, the recommended representation is the ordered sequence:

H=(T_real,0,T_real,1,...,T_real,n-1)

Together with the corresponding state sequence, this forms the canonical trajectory representation.

The primary comparison is exact trajectory equality:

H_A=H_B

or:

H_A≠H_B

No discretionary distance threshold is required for the initial fixture.

---

## 7. Minimal fixture construction

The fixture shall contain the following logical components:

1. fixture_config
2. state_constructor
3. context_constructor
4. tacc_constructor
5. x_declaration
6. realization_operator
7. transition_engine
8. trace_writer
9. trajectory_deriver
10. invariance_audit
11. integrity_manifest
12. preflight_runner

The realization_operator is the only component intentionally parameterized by X.

---

## 8. Separation of construction layers

The fixture shall maintain explicit separation between:

S,C,T_acc

and:

X

and:

T_real

and:

H

No component may silently modify a preceding layer.

The dependency direction shall be:

(S,C,T_acc,X) → T_real → S' → H

The fixture must expose sufficient intermediate data to audit this chain.

---

## 9. Preflight mode

The fixture shall support a non-scientific PREFLIGHT mode.

Preflight must verify:

1. deterministic construction;
2. S A/B equality;
3. C A/B equality;
4. T_acc A/B equality;
5. rules equality;
6. X declaration integrity;
7. X_A ≠ X_B;
8. trace completeness;
9. deterministic trajectory derivation;
10. manifest/hash integrity.

Preflight shall not produce a scientific result classification.

The preflight report shall explicitly state:

**NOT SCIENTIFIC EVIDENCE — FIXTURE INTEGRITY TEST ONLY**

---

## 10. Fail-closed rules

The fixture must fail closed if:

- S hashes differ;
- C hashes differ;
- T_acc hashes differ;
- any frozen rule hash differs;
- X declaration is absent or post hoc;
- X_A = X_B;
- trace fields are missing;
- trajectory cannot be deterministically derived;
- integrity manifest does not match;
- an undocumented manual intervention is detected.

No execution output may be promoted to scientific evidence after a fail-closed condition.

---

## 11. Integrity manifest

The fixture shall emit a manifest containing at minimum:

- protocol identifier and version;
- fixture identifier and version;
- source/fixture commit;
- environment identifier;
- S₀ hash;
- C hash;
- T_acc hash and cardinality;
- rule hashes;
- X declaration hash;
- trace hash;
- trajectory hash;
- generation timestamp;
- execution mode (PREFLIGHT or scientific mode);
- seed/randomization information where applicable.

The manifest must distinguish preflight from scientific execution.

---

## 12. Independent Executor-2 preparation

The fixture design shall support an independent reconstruction from a frozen package.

Executor-2 shall receive only:

- frozen protocol;
- frozen fixture;
- frozen configuration;
- frozen environment specification;
- execution instructions;
- audit worksheet.

Executor-2 shall not receive:

- Executor-1 trajectory;
- Executor-1 interpretation;
- post hoc tuning;
- expected result;
- scientific outcome.

## 14. Scientific boundary

This fixture design does not specify a scientific claim-producing scenario.

The actual scientific fixture instance must separately freeze:

- S₀;
- C;
- T_acc;
- X_A/X_B;
- realization mechanism;
- transition function;
- trajectory definition;
- seed/randomization policy;
- expected null/control conditions;
- environment;
- execution commands.

Those definitions belong in the operational bundle and must pass the pre-execution gates.
