## 1. Purpose

N-R3 verifies that the 58-dimensional Branch N representation `R` is not merely executable, but is explicitly and independently traceable to the normative definitions in N-R1.3 v0.2 and to the transformation system defined in N-R1.2.

N-R3 is an implementation/specification traceability gate. It is not a scientific result gate.

## 2. Preconditions

- N-R1.2: PASS / CLOSED
- N-R1.3 v0.2: PASS / CLOSED
- N-R2: PASS / CLOSED
- Branch N implementation present at `03_EXPERIMENTS/EMP-1.1/src/branch_n_r_v02.py`

## 3. Required traceability mapping

The implementation must expose the following canonical feature blocks, in exactly this order:

### R1 — Family availability (6)

1. `ADD_COMPONENT_available`
2. `REMOVE_COMPONENT_available`
3. `ADD_EDGE_available`
4. `REMOVE_EDGE_available`
5. `REWIRE_EDGE_available`
6. `MODIFY_RESOURCE_available`

Each feature must equal `1` iff the corresponding family has at least one element in `T_acc`, otherwise `0`.

### R2 — Family cardinality (6)

For each family in canonical family order, the feature equals the exact number of accessible transformations of that family.

### R3 — Component incidence (30)

For each component in canonical order `A1,A2,B1,B2,C1,C2`, five features are required:

1. ADD_COMPONENT incidence
2. REMOVE_COMPONENT incidence
3. ADD_EDGE incidence
4. REMOVE_EDGE incidence
5. REWIRE_EDGE incidence

Incidence must be calculated from transformation parameters in `T_acc`, not from outcome or future trajectory information.

### R4 — Transition-result structural signature (16)

The exact normative order is:

1. `n_delta_components_add`
2. `n_delta_components_remove`
3. `n_delta_edges_add`
4. `n_delta_edges_remove`
5. `n_delta_edges_rewire`
6. `n_delta_resources_up`
7. `n_delta_resources_down`
8. `n_noop`
9. `n_distinct_next_component_counts`
10. `n_distinct_next_edge_counts`
11. `n_distinct_next_resource_vectors`
12. `n_distinct_next_states`
13. `max_next_component_count`
14. `min_next_component_count`
15. `max_next_edge_count`
16. `min_next_edge_count`

These features must be computed from the canonical successor states generated by applying each transformation in `T_acc`.

## 4. Empty-accessibility boundary

If `T_acc = emptyset`, the implementation must return exactly 58 zeros. This includes all R4 min/max features. No current-state quantity may substitute for a successor statistic.

## 5. Independence requirement

N-R3 must not be satisfied solely by asserting that the implementation returns the expected dimension or by comparing the implementation output with another invocation of the same implementation.

The conformance harness must independently derive expected R1/R2/R3/R4 values from a fixed fixture and compare them feature-by-feature with `encode_r` output.

At least two non-empty fixtures with materially different transformation structures and one empty-`T_acc` fixture must be used. Fixture definitions must not depend on the historical EMP-1.1 result.

## 6. Anti-leakage checks

The harness must establish that R is invariant to objective identity when `S` and `T_acc` are held fixed, and that no future/outcome field is consumed by the encoder.

## 7. Acceptance criteria

N-R3 may be marked PASS only if:

1. all 58 positions have explicit specification mappings;
2. independent expected values match implementation values for every tested fixture;
3. canonical ordering is verified;
4. empty `T_acc` is exactly 58 zeros;
5. objective exogeneity passes;
6. no feature uses future trajectory/outcome information;
7. the implementation SHA is recorded;
8. the runner declares `scientific_execution = NOT_PERFORMED`.

Any mismatch is FAIL/BLOCKED and requires correction before proceeding.

## 8. Scientific boundary

Passing N-R3 establishes traceable implementation of the prospective Branch N representation. It does not establish:

- recovery of historical EMP-1.1 semantics;
- validity of the historical EMP-1.1 result for Branch N;
- causal efficacy of R;
- external/domain validity;
- confirmatory scientific success.
