# N-R4B.3 — Controlled Trajectory/Outcome Corpus Specification v0.1

**Date:** 2026-09-05  
**Status:** PROPOSED FOR PROSPECTIVE FREEZE  
**Branch:** N — Controlled New Reconstruction  
**Parent gates:** N-R4B.1 PASS/implementation semantics; N-R4B.2 PASS/CLOSED; N-R4A PASS/CLOSED; N-R3 PASS/CLOSED; N-R2 PASS/CLOSED.

## 1. Purpose and boundary

N-R4B.3 specifies the controlled corpus that will pair sealed N-R4A initial snapshots with trajectories and binary outcomes generated under the prospective Branch N semantics.

This is a **new controlled reconstruction**, not recovery of historical EMP-1.1/MVE-1.0 execution.

This specification authorizes corpus design only. It does **not** authorize learner fitting, hypothesis testing, model comparison, or confirmatory inference.

## 2. Corpus composition

The prospective corpus consists of two independent partitions:

- train: **30,000 episodes**;
- test: **10,000 episodes**.

Total: **40,000 episodes**.

Dataset generation is governed by N-R4A:

- train dataset seed: `3,100,000`;
- test dataset seed: `4,100,000`;
- episode identifiers: canonical zero-based integers within each partition.

The historical 20,000-episode pilot remains an unresolved historical/reconstruction item and is **not silently substituted** by the prospective 30,000/10,000 corpus.

## 3. Sealed initial snapshot boundary

For every episode, the predictor-side initial state `S_0` is generated by N-R4A and then treated as sealed input to R4B.

The trajectory generator may read only:

- the sealed `S_0`;
- the registered objective `o_0`;
- the registered horizon `H=6`;
- the frozen Branch N transformation/accessibility implementation;
- the episode-specific trajectory RNG.

It must not read future episodes, aggregate corpus outcomes, learner outputs, test performance, or recorded historical EMP-1.1 results.

## 4. Objective assignment

N-R4A assigns one objective from `O01..O12` to each initial snapshot. R4B does not alter that assignment.

The objective predicates are those prospectively reconstructed in N-R4B.1. They are not historical claims.

## 5. Trajectory generation

Each episode uses:

`trajectory_seed = dataset_seed + episode_id`

and a fresh `random.Random(trajectory_seed)` instance.

For `h=0,...,6`:

1. evaluate the registered goal predicate on the current state and fixed objective;
2. if the goal is true, terminate with `Y=1` and `GOAL_REACHED`;
3. if `h=6`, terminate with `Y=0` and `HORIZON_EXHAUSTED`;
4. enumerate `T_acc(S_h)` using the frozen Branch N implementation;
5. if `T_acc(S_h)` is empty, terminate with `Y=0` and `NO_ACCESSIBLE_TRANSFORMATION`;
6. sample uniformly from the ordered transformation list;
7. apply the selected transformation;
8. continue.

No artificial no-op is introduced. Distinct transformations yielding an identical successor remain separately selectable.

## 6. Corpus outputs

The corpus package must contain, at minimum, four logically separated artifacts per partition:

### A. Initial snapshots

One canonical record per episode containing:

`episode_id, components, edges, resources, objective`

plus partition-level metadata identifying the generator/specification versions and hashes.

### B. Trajectories/outcomes

One canonical trajectory record per episode using the N-R4B.1 schema:

`episode_id, dataset_split, dataset_seed, trajectory_seed, initial_snapshot_sha256, objective, horizon, steps, terminal_step, terminal_reason, outcome`

Each step contains:

`step, state_sha256_before, transformation_id, state_sha256_after`

### C. Predictor-side features

Predictor-side construction must be performed separately from trajectory generation.

For each episode, `B(S_0)` and `R(S_0)` may be derived only from the sealed initial snapshot. `R` must use the N-R1.3 v0.2 encoding and have exactly **58 numeric features**.

No trajectory field, terminal reason, outcome, post-transition state, or future information may enter `B` or `R`.

### D. Join manifest

A deterministic manifest may join predictor and outcome artifacts by:

`episode_id + initial_snapshot_sha256`

The manifest must verify one-to-one correspondence and reject missing, duplicate, or hash-inconsistent records.

## 7. Canonical serialization

All machine-readable corpus artifacts must use deterministic UTF-8 serialization.

For JSON/JSONL:

- sorted object keys;
- compact separators `(',', ':')`;
- `ensure_ascii=True`;
- newline termination for line-oriented records;
- canonical episode ordering by `episode_id`.

No hand editing is permitted after generation.

## 8. Required integrity checks

Before a corpus is accepted, the generation/conformance harness must verify:

1. exactly 30,000 train episodes;
2. exactly 10,000 test episodes;
3. unique episode IDs within each partition;
4. disjoint train/test episode-ID namespaces or an explicit partition-qualified key;
5. train/test dataset seeds exactly match N-R4A;
6. every snapshot satisfies N-R4A domain constraints;
7. every trajectory references the matching initial snapshot hash;
8. every trajectory has `0 <= terminal_step <= 6`;
9. every successful trajectory has `outcome=1` and `terminal_reason=GOAL_REACHED`;
10. every horizon failure has `outcome=0`, `terminal_reason=HORIZON_EXHAUSTED`, and `terminal_step=6`;
11. every empty-accessibility failure has `outcome=0` and `terminal_reason=NO_ACCESSIBLE_TRANSFORMATION`;
12. no trajectory contains more than six transitions;
13. all step indices are contiguous and ordered;
14. every `state_sha256_before` equals the canonical hash of the preceding state represented by the generated trajectory process;
15. every `state_sha256_after` equals the canonical hash of the applied successor;
16. canonical reserialization is byte-identical;
17. two independent runs with identical inputs produce identical artifact bytes and hashes;
18. changing only the registered dataset seed changes the generated corpus without mutating the generator specification;
19. predictor-side artifacts contain exactly the registered B/R inputs and no outcome-side fields;
20. the join manifest is one-to-one and hash-consistent.

## 9. Leakage checks

The corpus acceptance harness must explicitly inspect for:

- future-state information in predictor features;
- trajectory fields copied into predictor files;
- terminal reason or outcome copied into B/R;
- test outcomes or trajectories used during train generation;
- cross-partition state mutation;
- live registry/network access;
- ambient mutable cache dependence;
- post-generation manual modifications;
- dependence on learner output or model performance.

A leakage check that cannot be demonstrated is a blocking failure, not an assumed pass.

## 10. Distributional diagnostics — non-decisional

After integrity and leakage checks pass, descriptive diagnostics may be computed for corpus audit, including:

- component-count distribution;
- edge-count distribution;
- resource-value distributions;
- objective frequencies;
- outcome frequency;
- trajectory length and terminal-reason frequencies;
- `|T_acc(S_0)|` distribution;
- 58-feature missing/constant-value diagnostics.

These diagnostics are **not** permitted to change the frozen generator, objective codebook, R encoding, or corpus inclusion rules. They are audit outputs only.

No effect size, predictive score, or historical result may be used as a corpus-selection criterion.

## 11. Corpus-level acceptance gate

The corpus is accepted only if all mandatory integrity, determinism, schema, provenance, and leakage checks pass.

Any failure yields:

**N-R4B.3 — FAIL / BLOCKED**

and no learner fitting is authorized.

A successful corpus gate yields:

**N-R4B.3 — PASS / CLOSED**

and authorizes only the next explicitly defined predictor/outcome integration and learner-conformance stage.

## 12. Provenance package

The corpus package must record:

- N-R4A specification version and commit;
- N-R4B.1 semantic specification version and commit;
- N-R4B.2 conformance-gate commit;
- N-R2/N-R3 implementation and gate identifiers;
- R4A generator implementation hash;
- R4B trajectory implementation hash;
- Python/runtime identity;
- operating-environment identity sufficient for reproduction;
- dataset split, count, and seed;
- corpus artifact hashes;
- generation timestamp;
- conformance-run timestamp;
- canonical schema/version identifiers.

The provenance record must distinguish **SPECIFIED**, **RECONSTRUCTED**, **DERIVED**, and **VERIFIED** information.

## 13. Historical boundary

The existence or successful generation of this corpus must not be described as recovery of the historical EMP-1.1/MVE-1.0 dataset or generator.

The following remain explicitly prospective/reconstructed:

- objective predicates;
- trajectory policy;
- RNG derivation;
- empty-accessibility handling;
- duplicate-successor policy;
- canonical serialization.

## 14. Prohibited actions while N-R4B.3 is only proposed

Until this specification is prospectively frozen and its implementation passes conformance:

- do not generate the 40,000-episode scientific corpus;
- do not fit the HGB learner;
- do not compute confirmatory LogLoss differences;
- do not tune any generator choice to the historical `ΔLogLoss`;
- do not alter N-R4B.1 semantics based on pilot or test outcomes;
- do not substitute the historical 20k pilot without explicit provenance decision;
- do not claim empirical confirmation of TGCV.

## 15. Next gate

The immediate next gate is **N-R4B.3 implementation/conformance**, consisting of a deterministic corpus-generation harness plus independent integrity/leakage checks.

Only after that gate passes may the controlled 30,000/10,000 corpus be generated.
