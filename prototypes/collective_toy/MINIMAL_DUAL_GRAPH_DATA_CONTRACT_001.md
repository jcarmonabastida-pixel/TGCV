# Juguete Colectivo — minimal dual-graph data contract 001

**Status:** design proposal for review; not implemented or approved as a canonical TGCV schema.  
**Branch:** `design/condition-evaluator-contract-001-20261021`  
**Scope:** minimum logical data needed to preserve the system graph, represent a distinct TGCV graph, and demonstrate one traceable accessibility change.  
**Scientific boundary:** this contract specifies software representation and demonstration behavior only. It does not validate TGCV empirically or establish value causality.

## 1. Design rule

Keep two separately typed model layers in one demonstrator session:

1. **System model:** the familiar graph of states/configurations, transitions, execution conditions, and optional execution traces.
2. **TGCV model:** transformations, typed relations, accessible sets, accessibility-changing interactions/rules, and transformation trajectories derived under explicit rules.

The layers may reference one another, but one layer's objects must not silently become objects in the other. The schema below is a logical contract, not a JSON schema and not a proposed migration of the current executable input format.

## 2. Minimum logical entities

### 2.1 Shared model/session envelope

| Field | Required | Meaning |
|---|---|---|
| `model_id` | yes | Stable identifier for this demonstration model |
| `model_version` | yes | Version/revision of the input model |
| `active_route` | yes | `illustrative` or `user_model` |
| `system_model` | yes when available | The preserved system graph; may be absent only for a standalone TGCV illustrative case |
| `tgcv_model` | yes | TGCV representation, which may be incomplete |
| `mapping_records` | yes | Explicit links/rules between the two layers; may be empty |
| `provenance` | yes | Origin status and source/rule for relevant items and results |

### 2.2 System graph objects (Graph 1)

- **System node:** `id`, `label`, `node_type` (for example, state/configuration), and optional domain metadata.
- **System transition:** `id`, `source_node_id`, `target_node_id`, optional execution guard reference or condition text, and optional temporal prerequisites.
- **Scenario:** `id`, selected initial node where applicable, explicit facts/context, and disabled transition IDs.
- **Execution trace (optional):** ordered transition IDs and observed/resulting system node IDs, with the scenario and model version that produced the trace.

Condition representation remains a separate Layer B design decision. This contract does not authorize the pending typed-condition evaluator or schema v003.

### 2.3 TGCV graph objects (Graph 2)

- **Transformation:** `id`, `label`, and a statement of what operation/capability it denotes. A transformation is not a system state.
- **Typed relation:** `id`, `source_transformation_id`, `target_transformation_id`, `relation_type`, and a declared meaning/rule. A relation is not a system transition. A trajectory may use only relation types explicitly declared as trajectory-permitting.
- **Accessibility snapshot:** `id`, `system_or_domain_ref`, `scenario_ref`, and an explicit set of transformation IDs in `T_acc`. Each membership is either directly declared or derived under a named rule.
- **Interaction/mechanism:** `id`, `description`, and a declared rule reference. Its label alone never changes accessibility.
- **Mapping record (optional):** references source system objects and target TGCV objects, names a versioned mapping rule when derived, and records whether the mapping is declared, derived, illustrative, or unresolved.
- **Trajectory result (derived only):** ordered transformation IDs, relation rule/version, source accessibility snapshot, and derivation status. Do not produce this result until trajectory semantics are explicitly supplied.

### 2.4 Provenance record

Use exactly these origin labels in the initial demonstrator contract:

- `illustrative`: stipulated for teaching; not claimed to describe the user's actual system.
- `user_declared`: explicitly supplied by the user.
- `rule_derived`: generated by an identified, versioned rule from traceable inputs.
- `unresolved`: missing or unsupported information.

Every derived result must identify its input IDs, applicable rule ID/version, model version, and scenario. These labels describe provenance, not confidence or empirical truth. If a required input is unresolved, dependent results remain unresolved rather than being filled by inference.

## 3. Minimal relationships and derivation rules

1. System transitions connect system nodes only.
2. TGCV relations connect transformation objects only.
3. An accessibility snapshot contains transformation IDs, not system node IDs or transition IDs.
4. A mapping record may connect the layers only by explicit user declaration or a named/versioned rule.
5. A guard on a system transition affects TGCV accessibility only if an explicit mapping rule defines that effect.
6. An interaction changes `T_acc` or relations only through a declared rule with inspectable inputs and outputs.
7. A trajectory result is derived only from an accessibility snapshot and relation/trajectory rules that define which sequences are permitted.
8. Editing any dependency marks affected derived results stale until recomputed.
9. Illustrative assumptions remain labelled illustrative when copied for exploration; copying does not convert them into facts about the user's system.

## 4. End-to-end acceptance case

Use the stipulated artificial case in `TGCV_FIRST_DEMONSTRATION_CASE_001.md`. Acceptance is grouped around the user journey, not one test per schema field.

### Given

- Graph 1 has at least one system state and transition and is rendered with its original semantics.
- The TGCV illustrative case declares `T_acc_before = {a, b}`, `R_before = {(a,b)}`, and interaction rule `m` that adds `c` and relation `(b,c)`.
- The trajectory rule says a sequence is permitted only when all transformations are accessible and each adjacent pair is connected by an allowed compatibility relation.

### When

The user proceeds from Graph 1 to Graph 2, inspects the illustrative label and rule for `m`, and applies the rule.

### Then

- Graph 1 remains unchanged.
- Graph 2 identifies `a`, `b`, and `c` as transformations, and `m` as an interaction/mechanism.
- The before/after sets and relations are shown, with `T_acc_after = {a,b,c}` and `R_after = {(a,b),(b,c)}`.
- The derived difference is `ΔT_acc = {c}`.
- `[a,b]` is reachable before and after; `[a,b,c]` is newly reachable after applying `m` under the stipulated trajectory rule.
- Every derived output exposes its inputs and rule; all stipulated data remain labelled illustrative.
- No value score, empirical claim, or causal claim is produced.
- Editing the interaction rule marks dependent outputs stale; recomputation updates them consistently.

### Adversarial checks

Keep a small set of adversarial checks for the most consequential errors:
- A system transition is rejected as a TGCV relation endpoint.
- A system execution guard is not treated as an accessibility rule without an explicit mapping.
- A transformation absent from the accessible set is not used in a reachable trajectory.
- An unresolved relation or missing rule does not produce a supposedly complete derived trajectory.
- Import/export preserves layer types and provenance; changing a dependency invalidates prior results.

## 5. User route and missing information

Offer two explicit routes:

- **Explore an illustrative example:** a curated example with stipulated system/TGCV representations and persistent illustrative labels.
- **Build the TGCV graph for my system:** preserve Graph 1 and ask only for the next missing TGCV-specific input. The TGCV graph may remain incomplete until those inputs are supplied.

Switching routes must not overwrite the user's system graph or silently convert illustrative assumptions into user-declared facts.

## 6. Explicitly out of scope

This proposal does not settle:
- a universal ontology for TGCV;
- a final serialized schema, JSON schema, or migration version;
- the general semantics of all relation types;
- how empirical evidence determines accessibility;
- the observer/context value layer;
- approval or implementation of the condition evaluator;
- any scientific execution or claim of TGCV validation.

## 7. Review gate

Before implementation, review this logical contract alongside the functional architecture review, graph derivation contract, and first demonstration case. If accepted, the next engineering step is to map these logical entities onto the existing prototype without changing main, then implement one end-to-end case and the listed adversarial checks on a design branch. Synthetic tests establish only implementation conformance to this contract.
