## 1. Decision

Select **GitHub Artifact Attestations using Sigstore-backed OIDC signing**, generated by `actions/attest@v4`, with SLSA build provenance as the default predicate, and verified by GitHub CLI `gh attestation verify`.

This is the preferred trust mechanism for the TGCV repository because it binds an artifact digest to a GitHub Actions workflow identity and source repository/commit through a short-lived signing certificate and verifiable attestation. The Evaluator itself will not mint or self-assert trust.

Official technical references:
- GitHub artifact attestations: https://docs.github.com/en/actions/concepts/security/artifact-attestations
- Generate attestations: https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations
- `actions/attest`: https://github.com/actions/attest
- Verify: https://cli.github.com/manual/gh_attestation_verify

## 3. Attested subject and binding

The attested subject is the **final immutable Monte Carlo report package** produced by the technical workflow, not individual source files or documentation.

The package must contain or reference, by cryptographic digest:
- the report payload and report fingerprint;
- canonical evaluation SeedAssignment manifest and its recomputed fingerprint;
- calibration-bank manifest/fingerprint and disjointness validation result;
- effective Generator/DGP/Analyzer configuration payload and recomputed fingerprint;
- complete M/R/RunManifest reconciliation ledger;
- tested source commit and source-tree/archive digest;
- schema versions and validation outcomes.

The artifact attestation binds the final package digest to the workflow provenance. The package's internal manifest binds its constituent records to that digest. A report fingerprint alone is not an authenticity mechanism.

The attestation must be generated only after the package is finalized and hashed. Any later mutation creates a different subject digest and invalidates the binding.

## 4. Trusted builder and workflow identity policy

The signing operation must run in a dedicated, governed reusable workflow whose identity is pinned by the verifier and whose security-sensitive logic cannot be overridden by caller inputs.

Minimum policy:
- exact repository identity: `jcarmonabastida-pixel/TGCV` (also verify immutable repository identifier where available);
- exact signer workflow path and immutable revision/digest;
- expected OIDC issuer: `https://token.actions.githubusercontent.com`;
- expected source ref/commit and triggering context;
- least-privilege permissions, including `id-token: write` and `attestations: write` (and only additional documented permissions needed by the current action/API);
- no untrusted pull-request code or caller-controlled predicate fields may influence the signing step;
- pin third-party actions by full commit SHA, not mutable tags, in the governed workflow;
- attest only the final report package subject digest.

The verifier must use `gh attestation verify` with repository scope, expected signer workflow, expected predicate type and applicable source identity constraints. It must inspect verified certificate identity and timestamps, not trust arbitrary user-controlled predicate fields as cryptographic facts.

## 5. Verification states

Keep the Gate 159 three-level model:
- `PROVENANCE_DECLARED`: caller-provided metadata only.
- `PROVENANCE_RECONCILED`: deterministic seed/configuration/manifest joins pass.
- `PROVENANCE_AUTHENTICATED`: the report package digest has a valid external attestation and passes the governed signer/repository/source policy.

Only the third state may be called authenticated. If reconciliation passes but attestation is unavailable, the maximum state is `PROVENANCE_RECONCILED`. Missing, invalid, wrong-repository, wrong-workflow, wrong-commit, wrong-predicate or digest-mismatched attestations fail closed.

Attestation is evidence of where/how the package was produced under the workflow identity. It is not proof that the scientific design is valid, the data are truthful, the Analyzer is correct, or a causal claim is established.

## 6. Verification architecture

1. Evaluator performs deterministic seed-bank, M/R, RunManifest and effective-configuration reconciliation.
2. A report packager produces a deterministic final package and SHA-256 digest.
3. A trusted GitHub Actions reusable workflow builds/receives that exact package and creates the artifact attestation after finalization.
4. A separate verification step retrieves the attestation and runs `gh attestation verify` against the exact package, with repository and signer-workflow constraints.
5. A small adapter parses the verifier's structured result and applies the governed policy; it must not reimplement signature or transparency verification.
6. The report acceptance record stores package digest, attestation bundle/reference, verified signer identity, source commit, workflow/run identity, predicate type, verification timestamp/result and verifier version.
7. Any change to package, source identity or workflow policy requires fresh attestation and verification.

For offline verification, preserve the Sigstore bundle and trusted-root material, refresh trusted roots as required, and verify the certificate repository identifier against the expected immutable repository ID.

## 7. Required tests and policy checks

Before implementation is accepted, demonstrate:
- valid attestation for exact package and approved workflow is accepted;
- altered package digest is rejected;
- missing attestation is not authenticated;
- wrong repository or immutable repository ID is rejected;

## 9. Decision rationale and limitations

GitHub Artifact Attestations are preferable to a self-managed long-lived signing key because GitHub Actions obtains a short-lived Sigstore certificate through OIDC and the verification tooling checks signer identity and attestation integrity. A trusted builder is still required: the predicate body can contain workflow-controlled claims, so the verifier must pin the signer workflow and inspect only cryptographically grounded certificate/timestamp fields as authenticity evidence.

The attestation establishes artifact provenance, not scientific correctness or truthfulness of all claims inside the predicate. The report package's deterministic reconciliation remains a separate required control.
