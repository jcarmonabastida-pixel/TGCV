## 1. Purpose

Record the strategic direction agreed for the practical-application and transfer exploration of TGCV, together with the immediate execution boundary established in the continuation conversation.

The working premise is to search for **application fit** through structural problem classes and mechanisms rather than beginning from sectors. The purpose is opportunity discovery and transfer exploration, not scientific validation by application demand.

## 2. Product/application hypothesis

Two possible implementation forms are retained as hypotheses:

### A. Out-of-the-box analytical tool

A reusable **TGCV Foundations Core** providing the domain-independent analytical and translation foundations, complemented by domain-specific connectors/adapters.

Conceptual form:

`TGCV Foundations Core + Domain Connector(s) → domain-native TGCV analytical workflow`

The Foundations Core would conceptually preserve the governed distinctions among state, candidate transformations, accessibility, `T_acc`, `ΔT_acc`, Reach, Trajectory, Outcome and Value, while connectors would translate domain-native representations into the common protocol without erasing their native semantics.

### B. Bespoke implementation

Where a reusable product architecture is premature or domain integration is highly specific, a software/custom implementation route remains available:

`client/system context → setup + multi-domain translation protocol → domain-specific implementation → controlled deployment`

This is an application hypothesis, not an established product architecture or commercial proposition.

### WP2 — Mechanism-first application-fit discovery

After WP1, instrument an iterative discovery process around eight structural problem mechanisms:

1. opening options;
2. closing options;
3. reordering options;
4. making alternatives mutually incompatible;
5. creating new capabilities;
6. removing capabilities;
7. changing the cost/time of transformations;
8. changing the constraints that determine `Pτ`.

The search should ask:

> Where does a real operational problem involve an intervention or event that changes what transformations become accessible afterwards, and where is that change potentially useful to represent before downstream outcomes are observed?

### WP3 — Case capture and categorisation

Each emerging practical case should be documented separately before being promoted to the MOI.

Minimum case record:

- problem statement;
- mechanism class(es);
- target system/domain;
- decision unit and decision-time boundary;
- state/context;
- candidate transformations;
- hypothesised accessibility change;
- downstream trajectory;
- measurable operational consequence;
- available data;
- likely integration point;
- potential TGCV role;
- implementation form: Foundations+Connector / bespoke;
- evidence maturity;
- scientific evidence gap;
- transfer opportunity;
- partner ecosystem;
- explicit non-claims.

Cases do not need scientific evidence to be documented as transfer opportunities. Their scientific status must nevertheless remain explicit.

### WP4 — Industrial Opportunities Map update

MOI should be updated with the most relevant opportunity cases once the discovery process has generated sufficiently concrete descriptions.

MOI inclusion is a **transfer/opportunity decision**, not a scientific-evidence admission. Opportunity relevance may therefore be high even where scientific evidence is absent, provided the distinction is explicit.

### WP5 — Partnership exploration

Explore public and private-sector alliances around the concrete cases that emerge.

The preferred sequence is:

`mechanism → practical problem → concrete case → application hypothesis → integration requirements → potential partner`

rather than:

`sector/organisation → presumed use case → retrofit TGCV justification`.

## 6. Application-fit lens

A practical case becomes especially interesting when several of the following coexist:

1. an explicit or reconstructable action/transformation space;
2. an intervention that can alter that space before the downstream result;
3. a sufficiently observable subsequent trajectory;
4. a consequential operational decision or cost of error;
5. existing or realistically obtainable state/action/outcome data;
6. a natural place where a TGCV representation could be integrated into an existing workflow;
7. a measurable baseline and operational consequence;
8. a plausible path to independent reproduction.

This is a discovery heuristic, not a scientific score or formal validity criterion.

## 7. Architectural implication

The mechanism-first search should explicitly test whether recurring application cases share a common domain-independent interface.

Potential emerging architecture:

`Domain system → connector → TGCV Foundations → analysis/decision interface → connector/domain system`

The connector boundary should preserve domain-native semantics while exposing the common TGCV protocol. If recurring cases instead require fundamentally incompatible representations, that result should be retained as an architectural boundary rather than forced into a common product.

## 8. Scientific protection

Application demand must not drive retrospective scientific confirmation. In particular:

- an attractive use case is not evidence for TGCV;
- customer/partner interest is not scientific validation;
- technical feasibility is not causal evidence;
- measurable operational benefit is not automatically TGCV Value;
- a successful connector is not evidence of transversal validity;
- absence of scientific evidence does not prevent an opportunity from being recorded in MOI;
- scientific claims remain governed by RMA/Matrix and their specific evidence gates.

## 9. Suggested iteration loop

`Mechanism class`
`→ broad problem discovery`
`→ candidate practical cases`
`→ structured case record`
`→ application-fit assessment`
`→ categorisation`
`→ opportunity selection`
`→ MOI update`
`→ partner/ally exploration`
`→ feedback into next discovery iteration

The loop should be lightweight at discovery stage and become progressively more formal only when a case approaches controlled technical or scientific execution.
